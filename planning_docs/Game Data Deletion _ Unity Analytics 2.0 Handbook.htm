Game Data Deletion

Game Data Deletion is the process that deletes* all the user data on a Unity environment, whilst still keeping things like saved data explorer reports, funnels, custom events available. The "deleted" user data is then marked for deletion which will execute actual deletion after some to-be-decided time period (i.e. 30-90 days). This is very similar to how deletions work in deltaDNA.

info

When we manually (or the customer via self-serve) choose to 'delete' data, what actually happens internally is the Unity environment id is transferred to another DDNA environment. Any entities that are mapped to the DDNA env id (such as events) are cloned. Entities mapped onto the Unity environment id can remain as they are. User data remains on the old DDNA environment and therefore becomes not queryable by the customer.

The ADR for the decision to do the deletion via this environment-id flipping method can be found here.

Technical Overview#

What actually happens:

  1. Unity environment id is received, this will be the source environment
  2. A new DDNA environment is created
  3. Clone necessary entities:
    1. Data explorer reports are cloned in the chart service onto the new environment
    2. Events are cloned in the event service onto the new environment
      1. Environment specific metrics (ENVIRONMENT_SPECIFIC_METRICS table) are not cloned. There is an ETL which runs every 5 min and creates the event count metrics etc. Thread on this
      2. The JSONTREE_ID column remains the same as that is not being cloned.
  4. The source DDNA environments unity-environment-id field is set to null, deleted is set to true, and the DDNA name is extended with underscore and 4 extra characters as to avoid uniqueness restriction
  5. The new DDNA environments unity-environment-id field is set to the relevant Unity environment and the DDNA name is set to the one on the old environment

How to request for the game data deletion for the customers#

  1. Add request to this spreadsheet to keep track of all requests.
  2. Post a message to #devs-curiosity saying that you have a request from the users for game data deletion.

How to perform the game data deletion#

The manual process is done by sending a POST request to "/v1/environments/UNITY-ENV-ID/data-deletion" on the auto-provisioning service. Replace UNITY-ENV-ID with the Unity environment that should have its data deleted. You will need to get the API key for the auto-provisioning service (see below).

Follow these steps to delete data for the environment:

  1. Post a message to #devs-curiosity saying that you're going to be doing manual data deletion on a specific unity env

  2. Get UNITY-ENV-ID

  3. Be on the VPN

  4. Get the api key to make a call to the auto-prov service:

    1. Have gcloud and kubectl installed (or some other way of getting kubernetes secrets)
    2. Point gcloud towards prod
    Point to the production project
    gcloud container clusters get-credentials unity-loh-prd-3-euw1 --region europe-west1 --project unity-ads-liveopshub-prd

    1. Get permissions to view secrets: You can do this with CanHaz by typing /request-access anywhere in Slack and select

      • Project: unity-ads-liveopshub-prd
      • Role: the Kubernetes Engine Developer

    2. In google cloud console, get the API key (this may not work on Windows, see below):

    Get API Key
    kubectl get secret --namespace loh-analytics-auto-provisioning api-key -o jsonpath --template '{.data.key}' | base64 -d
    1. If on Windows, remove the | base64 -d part. You will need to find a way to decode the returned string from base64
  1. Optional: If using something like Postman, consider setting the Unity environment ID and API key as global variables, then automatically wiping them right after sending the request just to be safe. Example:
  1. Send a POST to loh-analytics-auto-provisioning.prd.mz.internal.unity3d.com/v1/environments/UNITY-ENV-ID/data-deletion. Make sure the header x-api-key is set to the API key you just got.
Send request to delete game data to the specific environment
curl --location --request POST ‘https://loh-analytics-auto-provisioning.prd.mz.internal.unity3d.com/v1/environments/{UNITY_ENV_ID}/data-deletion’ \
--header ‘x-api-key: {api-key-here}’

The response will contain the new DDNA environment ID that the Unity environment now points at. Put this in the spreadsheet linked below. If the request failed for whatever reason you should let #devs-curiosity know.

  1. Update the spreadsheet to keep track of all requests.

  2. When notifying the customer their data has been deleted, it would be nice to:

    1. Find out why they wanted to do data deletion
    2. Tell them that they should be using environments to split data (i.e. they shouldn't be testing on production and then wiping before release)

How to manually rollback:#

Make #devs-curiosity aware something has gone wrong, and probably get them to do it for you. You're going to attempt to undo the changes that this method will have done.

At the time of writing, these are the things that will need to be changed back in the environments table:

  • unity_environment_name - Set to null on new env, Remove the _deleted part on the old env to reset it back
  • unity_environment_id - Set to null on new env, and set back on the old env
  • name - Set the name to the old one that the new env took over and update the new env to have extra characters at the end
  • deleted - Set to 0 on old env, 1 on new env
